The wallet UI offers explicit payment-network selection and pins Circle's exact contract for each chain. New EVM signatures verify their on-chain domain separator before signing. Solana and Cardano use the same agent tools with their native isolated-account policy IDs; no general signing or arbitrary transaction interface is exposed.

## Setup and spending rules

1. Start the updated local desktop build with `MAGICMONEY_X402=1` in its environment. In PowerShell, set `$env:MAGICMONEY_X402='1'` before launching the updated executable or running `npm run dev`. An already-running process needs a restart (which stops its policies and pairings). This change does not update an installed release, enable the flag on an existing wallet or fund anything.
2. Enable Agent Access and pair an assistant with request permission. Authorize an existing isolated spending account as described in [Agent execution](AGENT-EXECUTION.md). Its ETH limits remain ETH limits; they do not authorize USDC spending.
3. Expand **USDC x402 on this account**. Enter 1–20 exact HTTPS resource URLs, a per-payment USDC cap, rolling 24-hour cap and lifetime USDC budget. Authorize with the wallet password. These asset-specific terms are immutable; use a new isolated account to change them. Recipient allowlist, owner/grant binding, expiry and Stop controls come from the existing account.
4. Fund only that displayed isolated address with the intended USDC on Base (Base Sepolia in Testnet Mode). Its index starts at 1000 and uses the same wallet seed. No main-account access, automatic top-up or separate x402 spending account is added.

An in-policy payment signs automatically. A well-formed supported request outside the URL, recipient or USDC caps enters the same inbox for an explicit one-payment override. A missing USDC rule also requires review. Malformed/unsupported input or a stopped, expired, revoked, locked or unavailable account is rejected; approval cannot bypass these authority and signing checks.

Budgets charge the entire authorization amount durably before signing, including manual exceptions and failed/uncertain attempts. Expiry, failure, revoke and restart never refund the lifetime budget. The rolling window counts reservations in the last 24 hours. This bounds authority issued, rather than trusting a merchant's settlement report. Stop all/Stop account prevent future signatures; they cannot recall one already released. Restart stops the parent policy and invalidates its pairing.

**Recovery limitation:** **Recover ETH** handles native ETH only. USDC uses the same displayed seed derivation path but currently requires manual recovery in a trusted wallet supporting that path, with Base ETH for fees. Keep that path with the offline seed backup; do not delete journals to reset budgets.

Use current **x402 v2** HTTP headers: `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE`. The brief's `X-PAYMENT` names are v1; reject rather than infer or silently translate versions.

## Authority boundary

The token signature enforces **chain, token contract, sender, recipient, exact base-unit amount, validity interval and single-use nonce**. It does **not** enforce resource URL, grant ID, HTTP method, successful resource delivery or a refund. Grant/account/mode/URL binding is enforced by wallet records and authenticated retrieval. Never describe that URL binding as a token-contract guarantee.

Once released, an authorization may be redeemed until its signed expiry, even if the wallet is locked, the assistant is revoked or the app exits. Local revocation prevents future signing/retrieval but cannot recall an existing signature. Replaying the same payload can spend at most once on the canonical token contract; an agent can copy it. Delivery over HTTP cannot provide literal exactly-once delivery: retries must return the same authorization, not generate a new nonce/signature. The UI must disclose these facts before approval.

## Flow

```mermaid
sequenceDiagram
    participant A as Paired agent
    participant S as Resource server
    participant W as Wallet main process
    participant U as Wallet owner
    participant F as Facilitator
    A->>S: Request resource
    S-->>A: 402 + PAYMENT-REQUIRED
    U->>W: Authorize USDC rules on existing isolated account
    A->>W: propose_x402_payment(policyId, requestId, resourceUrl, paymentRequired)
    W->>W: Validate binding and current account/USDC rules
    alt Valid payment outside automatic rules
        W-->>A: Pending approval ID and unsigned metadata
        U->>W: Review stored request and explicit exception
        W-->>U: Full URL, isolated account, recipient, amount and expiry
        U->>W: Approve one payment
    else Within authorized rules
        W->>W: Automatic authorization allowed
    end
    W->>W: Verify chain, token/domain, balance, nonce and transfer simulation
    W->>W: Audit + durable nonce reservation; sign and verify; seal payload
    W-->>U: Authorization status (no signature)
    A->>W: x402_payment(proposalId, requestId, resourceUrl)
    W->>W: Recheck grant/context/expiry; audit before release
    W-->>A: Same bounded PAYMENT-SIGNATURE payload on idempotent retry
    A->>S: Original request + PAYMENT-SIGNATURE (no redirect forwarding)
    S->>F: Verify and settle
    F-->>S: Settlement result
    S-->>A: Resource + PAYMENT-RESPONSE
```

The wallet does not fetch arbitrary resource URLs or contact agent-supplied facilitators. The agent owns transport. A 200 response or facilitator claim is not wallet-verified settlement. The wallet records authorization issuance, not payment completion; verification of settlement remains a separate on-chain operation.

## Data and validation

```ts
type ProposeX402 = {
  policyId: string // existing isolated spending account, never the main account
  requestId: string
  resourceUrl: string
  paymentRequired: {
    x402Version: 2
    resource: { url: string; description?: string; mimeType?: string }
    accepts: [{
      scheme: 'exact'; network: 'eip155:8453' | 'eip155:84532'
      amount: string; asset: string; payTo: string; maxTimeoutSeconds: number
      extra: { name: string; version: '2'; assetTransferMethod?: 'eip3009'; paymentFlow?: 'authorization' }
    }]
    error?: string
    extensions?: Record<string, never>
  }
}
```

- Strict JSON shape and size bounds; reject extra signing/domain/nonce/validity fields. One payment option only; reject ambiguous arrays, unsupported extensions and schemes. Server descriptions are plain untrusted text, never HTML/instructions.
- HTTPS canonical URL, no credentials/fragments/IP literals/nonstandard ports/private hostnames; full URL including query must match `resource.url`. Never dereference the URL in the wallet. Show ASCII hostname/full URL to expose lookalikes.
- Pin USDC asset addresses by numeric chain ID, not symbol. Base: `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`; Base Sepolia: `0x036CbD53842c5426634e7929541eC2318f3dCF7e`. Mainnet/testnet must match the paired mode. Reject disabled/unavailable chain RPCs.
- Amount is a positive canonical integer string within uint256, interpreted with pinned USDC decimals (6). No floating point, fiat conversion, exponent notation, ticker matching or automatic alternative selection. Recipient must be a nonzero valid EVM address.
- Fixed EIP-712 `TransferWithAuthorization` type only. Domain name/version must match the pinned token and its on-chain domain separator. Sender is derived from the bound isolated spending account; agent input never supplies an arbitrary sender or derivation index.
- Wallet generates a random 32-byte nonce, reserves it durably and checks token `authorizationState`. Wallet chooses validAfter (five seconds before creation) and validBefore from its clock, bounded by parent/grant expiry and server timeout (15–300 seconds accepted); never more than five minutes after creation, no hidden extension on retry. Display both times and nonce in the record/review.
- Read chain ID, domain separator, decimals, balance and sender code; simulate the unsigned ERC-20 transfer, without sending a redeemable signature to an RPC provider. Recheck authorization/context/time after every asynchronous boundary. Actual facilitator verification/settlement is outside the wallet.
- A requestId maps to immutable input, one nonce and at most one signed authorization. Changed URL/amount/recipient/token/domain under that ID is rejected. An interrupted signing attempt cannot be re-signed automatically. Lock, Privacy Mode, account/mode change, revocation, expiry and feature flag deny new signing/retrieval.

Tools: `wallet_propose_x402_payment`, `wallet_x402_payments` (own unsigned/status views and USDC limits), `wallet_x402_payment` (retrieve this request's authorized payload). CLI names are `propose-x402-payment`, `x402-payments`, `x402-payment`. No agent approval, rejection override, policy creation, raw typed-data signing or settlement endpoint. The existing MCP `tools` command returns complete schemas. Read-only pairings cannot bypass discovery by calling these tools directly.

To pay: decode the merchant's `PAYMENT-REQUIRED` header and submit `{policyId, requestId, resourceUrl, paymentRequired}`. Poll `x402-payments` only if awaiting owner review. Then call `x402-payment` with `{proposalId, requestId, resourceUrl}`. It returns `{headerName: 'PAYMENT-SIGNATURE', headerValue, expiresAt}`. Retry the original resource using that header without forwarding it to redirects. Treat the header as a spend credential; never log it or include it in a conversation. Retrying the same wallet request returns the same nonce/payload; never create a new request ID to replace an uncertain payment.

## Storage, audit and UI

The main process keeps an OS-sealed atomic journal containing bindings, nonce reservation, times, status and any approved payload. Damage, OS storage unavailability and write failures fail closed; no silent reset. Session-only grants die on restart. Persisted pending reviews expire on restart; issued signatures retain their original expiry. Audit uses existing bounded activity records with client label/time/action/outcome only, no URL, requirements, signatures, credentials or provider errors. Audit must succeed before signing/releasing a payload.

The same Agent Access panel contains USDC rules beneath each isolated account and an x402 inbox above the account list. It shows assistant, full URL, network, sender, exact USDC base units plus human amount, asset contract, payTo, nonce, both validity times, policy exception reasons and state. **Review USDC exception**, **Reject USDC payment** and **Approve one USDC payment** are native wallet actions. Approval returns metadata only; the renderer never receives the spendable signature/header. The prompt explains that this overrides the displayed policy restrictions for one payment, authorizes a third-party USDC transfer, and does not prove resource delivery or settlement. Feature-off exposes no executable x402 tool/UI and preserves legacy proposal and ETH execution behavior.

| Threat | Control / limit |
|---|---|
| Malicious requirements/domain/amount | Strict closed schema, exact token+chain pins, fixed EIP-712 type, independent on-chain domain checks |
| Cross-account/grant/URL substitution | Immutable stored binding, sender derivation, matching retrieval tuple, context check after async work |
| Double approval/retry/crash | Durable reservation before signing, one authorization per request, same payload on retry, no automatic replacement |
| URL spoofing/SSRF/prompt injection | Canonical HTTPS, plain escaped display, no wallet URL fetch, no server-supplied HTML or instructions |
| Signature copied after release | Short signed expiry, exact amount/payTo, token-enforced single-use nonce; local revocation cannot undo release |
| Audit/disk failure | Fail closed before signature release; preserve journal, never reset to make an error disappear |
| Forged facilitator success/resource response | Do not mark settled/delivered from unverified response; signature issuance is separate from receipt proof |
| Compromised OS/main/renderer | Existing wallet trust boundary; local grants/feature flags do not protect a stolen seed or compromised main process |
