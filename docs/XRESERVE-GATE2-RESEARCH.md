# xReserve gate 2 research — 2026-09-27

This is a read-only research handoff for inbound USDC → Cardano USDCx. It does not authorize a live transfer or establish an executable quote.

## Verified interface

- Circle's [Cardano deposit quickstart](https://developers.circle.com/xreserve/tutorials/deposit-usdc-into-xreserve) documents `depositToRemote(value, remoteDomain, remoteRecipient, localToken, maxFee, hookData)` and a Cardano Preprod example. `remoteDomain` is 10004 on both testnet and mainnet. The example's `DEPOSIT_AMOUNT = 20` and `MAX_FEE = 10` are sample inputs, **not** a published minimum or charged fee.
- For a Cardano base or enterprise address, Circle's [quickstart](https://developers.circle.com/xreserve/tutorials/deposit-usdc-into-xreserve) encodes `remoteRecipient` as a 4-byte key/script credential tag plus the 28-byte payment credential. Enterprise addresses use empty `hookData`; base addresses use 66 zero bytes, a 1-byte staking credential tag, and the 28-byte staking credential. The sample checks address type but a wallet implementation must also check exact length and network ID before constructing a mainnet transaction.
- Circle's [supported domains table](https://developers.circle.com/xreserve/references/supported-blockchains-and-domains) lists the mainnet xReserve contract as `0x8888888199b2Df864bf678259607d6D5EBb4e3Ce` for both Ethereum and Arc, Ethereum USDC as `0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48`, and Arc USDC as `0x3600000000000000000000000000000000000000`. Cardano USDCx is asset unit `1f3aec8bfe7ea4fe14c5f121e2a92e301afe414147860d557cac7e345553444378`.

## Attestation observation

- On 2026-09-27, a read-only GET to Circle's [attestation-by-source-transaction endpoint](https://developers.circle.com/api-reference/xreserve/all/get-attestations-by-tx-hash) for [Ethereum transaction `0x6a7f66cb047de10b8db091403dac8791ad291e9c501f734fbdde65e20aae2c99`](https://etherscan.io/tx/0x6a7f66cb047de10b8db091403dac8791ad291e9c501f734fbdde65e20aae2c99) returned HTTP 200 and one attestation with `remoteDomain: 10004`, a payload, and a message hash. This shows Circle produced a Cardano-directed attestation for that source transaction. It does **not** prove the recipient received USDCx, what Cardano fee was charged, or that 3.981721 USDC is an accepted mint minimum. See [the earlier event analysis](CARDANO-RESEARCH-NOTES.md).

## Open gate

Circle's [contract source](https://github.com/circlefin/evm-xreserve-contracts/blob/master/src/modules/x-reserve/DepositToRemote.sol) defines `maxFee` as a cap and emits it with the deposit; it does not disclose the fee charged by the remote mint. [IOG portal terms](https://usdcx.iog.io/docs/USDCx_portal_terms_of_use.pdf) say the mint fee can vary and is displayed before confirmation. The public mint measured below is one historical sample, not a live quote, minimum, or fee schedule. Read-only mint correlation and source-to-attestation checks are implemented but not integrated into swap execution; fee and minimum-deposit terms remain unresolved before an executable gate 2 route. No live transfer was made for this note.

- A read-only Koios [`tx_cbor`](https://api.koios.rest/#post-/tx_cbor) request for that Cardano transaction exposed the mint redeemer's CBOR. Its indefinite byte strings contain Circle's **335-byte attestation payload and 65-byte signature byte for byte** (the payload is CBOR-chunked as five 64-byte pieces and one 15-byte piece). - Two other recent [USDCx mint-history](https://api.koios.rest/#get-/asset_history) entries, `dee1a2f3…4061e3a4` (299.846174 minted) and `f9cfe113…293b1e` (2,500 minted), also allocate exactly **one base unit** to the same secondary address and the remainder to a recipient, according to Koios [transaction UTxOs](https://api.koios.rest/#post-/tx_utxos). ## Implementation progress

The repo now has isolated modules for Cardano-recipient encoding and EVM xReserve call validation (`src/main/xreserve-cardano-deposit.ts`), Ethereum source proof (`src/main/xreserve-ethereum-deposit-proof.ts`), source-to-Circle attestation correlation (`src/main/xreserve-source-attestation-link.ts`), attestation-to-Cardano-mint proof (`src/main/xreserve-cardano-mint-proof.ts`), bounded recipient and global asset scanners (`src/main/xreserve-cardano-mint-locator.ts`, `src/main/xreserve-cardano-mint-audit.ts`), read-only Blockfrost/Circle adapters (`src/main/xreserve-cardano-provider.ts`), and a read-only Ethereum mainnet evidence reader (`src/main/xreserve-ethereum-evidence-reader.ts`). The public 95-zero-byte-hookData deposit cannot pass the wallet's approval rules; the positive Ethereum source and attestation-link tests are synthetic. These modules are not wired to signing, submission, routing, sessions, or UI. The actual fee/minimum quote remains an explicit gate for enabling transfers.

## Status-reader limitation — 2026-09-27

The wallet's current read-only mint locator walks the approved address's transaction history. That is sufficient to find a mint that actually credits the approved address, but it cannot discover a Cardano mint sent **only to a different address**, because that transaction is absent from the approved address's history. [Blockfrost documents address transactions and global asset history as separate reads](https://docs.blockfrost.io/). A future status integration should either obtain an issuer-supported lookup by Circle message hash or add a bounded scan of USDCx mint history before interpreting a prolonged “awaiting mint” state as anything more than pending/unknown. No terminal failure or refund should be inferred from absence in one address history.

### Global lookup option — 2026-09-28

Blockfrost's [current OpenAPI specification](https://github.com/blockfrost/openapi/blob/master/blockfrost-openapi.yaml) defines `GET /assets/{asset}/transactions` with `from=block_height[:tx_index]` and `to=...` inclusive filters, `order=asc`, and rows containing `tx_hash`, `tx_index`, `block_height`, and `block_time`. It includes **all USDCx transactions**, not only mints, so a global check should be bounded, resumable, and invoked less often than the recipient-address check. A matching Circle attestation in a confirmed USDCx mint paid elsewhere would surface as a conflict through the pure verifier. The specification's `GET /assets/{asset}/history` returns mint/burn actions, but offers only page, count, and order, so its moving pages are less suitable for a durable cursor. Neither endpoint proves an absence is final; a scan reaching today's tip means only “not found yet.”

### Current portal fee display — 2026-09-28

The [IOG bridge page](https://usdcx.iog.io/bridge) currently loads a mainnet [configuration bundle](https://usdcx.iog.io/_next/static/chunks/97e7cad71074aa8f.js) with `deposit: { maxFee: 10, typicalFee: 0 }`; its [fee-display bundle](https://usdcx.iog.io/_next/static/chunks/0add918ed2cfd9fd.js) renders the Ethereum route's typical fee and maximum from those values. This is the Portal's current frontend configuration, **not** a published fee API, guarantee, or minimum deposit. The [Portal terms](https://usdcx.iog.io/docs/USDCx_portal_terms_of_use.pdf) allow fees to change and say current fees appear before confirmation. Do not hardcode `0` or `10` as the wallet's executable quote.

On 2026-09-29 UTC I checked the scripts loaded by the [Portal bridge page](https://usdcx.iog.io/bridge). The [configuration bundle](https://usdcx.iog.io/_next/static/chunks/97e7cad71074aa8f.js) has `withdrawal: { minAmount: 5, feeEstimation: 5 }`, while its deposit settings have no `minAmount`. The `5` is therefore a **withdrawal** setting and must not be presented as an Ethereum-to-Cardano deposit minimum. The [bridge form bundle](https://usdcx.iog.io/_next/static/chunks/30cd41a48878c1de.js) rejects an amount that is empty or not positive, but that client-side check does not establish what the bridge operator will process. A further scan of the bridge page's loaded scripts found a `/fees` call in a [shared chunk](https://usdcx.iog.io/_next/static/chunks/8084ddff25a91cc7.js), but it is a Circle Iris forwarding-fee call for a burn/withdrawal route, not an Ethereum-to-Cardano deposit quote. I found no deposit fee-quote call or published deposit minimum in the scripts loaded by that page; this is a bounded inspection of current frontend code, not proof that no such interface exists elsewhere.

### Read-only provider wiring research — 2026-09-28

The official [Blockfrost OpenAPI specification](https://raw.githubusercontent.com/blockfrost/openapi/master/openapi.yaml) documents the reads needed by the existing locator and global audit: `GET /addresses/{address}/transactions` and `GET /assets/{asset}/transactions` for inclusive `from=block_height[:tx_index]` history, `GET /txs/{hash}` for confirmed transaction details, `GET /txs/{hash}/cbor` for full transaction CBOR, `GET /txs/{hash}/utxos` for outputs, and `GET /blocks/latest` for the indexed tip. The same specification lists 402 (daily quota), 403 (authentication), 418 (flood ban), 429 (rate limit), and 5xx (service failure), all of which must stay retryable or visibly unavailable rather than becoming an absence verdict. Blockfrost's documented responses establish provider shapes; they do not by themselves establish that two successive reads came from the same chain tip.

Circle's [attestations-by-source-transaction API](https://developers.circle.com/api-reference/xreserve/all/get-attestations-by-tx-hash) is `GET /v1/attestations?txHash=0x…` and returns an `attestations` array, potentially with more than one remote domain. The caller must preserve the exact requested source hash alongside the response because the response object does not echo that hash. The pure proof module already rejects ambiguous or contradictory attestations. This API is a status/evidence source, not a bridge fee or minimum-deposit quote.

### Source-to-attestation binding — 2026-09-29

[Circle's `DepositedToRemote` event definition](https://github.com/circlefin/evm-xreserve-contracts/blob/master/src/modules/x-reserve/DepositToRemote.sol) includes the depositor, `remoteToken`, `maxFee`, and `hookData` in addition to amount, local token, destination domain, and recipient. The current wallet source verifier checks the event against the approved Ethereum call, while `validateXReserveAttestation` checks only amount, domain, payment credential, and Ethereum USDC against the approved terms. A future status coordinator must compare **all corresponding fields** in the validated Circle payload with the verified source event before treating the attestation as belonging to that approved deposit. In particular, the remote token must come from the verified event; it is not a free-standing constant established by the present builder.

The repo now has that pure correlation check in `src/main/xreserve-source-attestation-link.ts` and a one-shot read-only coordinator in `src/main/xreserve-inbound-status.ts`. As of 2026-09-29, neither is connected to a fund-moving route or persisted swap session. The public Ethereum deposit with undocumented 95-zero-byte hookData remains intentionally outside the wallet builder's approved format, so positive source-to-mint test cases are synthetic.

### Questions requiring operator guidance before an executable route — 2026-09-29

The [Circle Cardano quickstart](https://developers.circle.com/xreserve/tutorials/deposit-usdc-into-xreserve) explicitly targets developers integrating xReserve into their apps and demonstrates a direct `depositToRemote` call from Ethereum Sepolia to Cardano Preprod. Thus direct third-party deposit integration is documented for **testnet**. The guide supplies a sample amount and `maxFee`, while the [IOG Portal](https://usdcx.iog.io/bridge) shows current fee text and the [Portal terms](https://usdcx.iog.io/docs/USDCx_portal_terms_of_use.pdf) allow fees to change. I could not establish from these sources a supported machine-readable **mainnet deposit** quote or a guaranteed minimum that a third-party wallet can use. Remaining questions for Circle/IOG: (1) a supported fee and minimum-deposit interface for direct Ethereum mainnet `depositToRemote` calls to Cardano domain 10004; (2) how to choose `maxFee` and what happens if that cap is below the Cardano minter's required fee; (3) whether mainnet has additional processing conditions beyond the documented testnet quickstart; and (4) the meaning and persistence of the observed one-base-unit USDCx allocation to a secondary Cardano address. Do not infer these answers from historical mints or the Portal's current frontend constants.

After a systematic check of Circle's [complete documentation index](https://developers.circle.com/llms.txt) and [xReserve OpenAPI specification](https://developers.circle.com/openapi/xreserve.yaml) on 2026-09-29, Circle does document a fee-calculating `POST /v1/prepare-withdrawal` for **Cardano USDCx burns and withdrawals**. The xReserve spec's eight paths contain no deposit fee or minimum-amount quote endpoint. That narrows the gate 2 unknown; it does not turn the withdrawal preparation endpoint into an inbound deposit quote. See [gate 3 research](XRESERVE-GATE3-RESEARCH.md) for the documented withdrawal and status APIs.
