# Working on MagicMoney Wallet

This is a **self-custody, multi-chain wallet** shipping as three targets from
one codebase (Electron desktop, Chrome MV3 extension, Android via Capacitor).
It holds real private keys and moves real funds across ~19 chains. Mistakes
here are not "revert and retry" — they can be irreversible fund loss for a
real user. Read this file before making changes; it exists because a change
made without this context broke a release (see "Incidents" at the bottom).

For feature/architecture background (supported chains, install instructions,
dApp connectivity, security model, project structure) read **README.md**
first — this file is deliberately just the operating rules and sharp edges,
not a re-description of what's already documented there.

## Ground rules

- **Never guess.** If a requirement, API contract, or expected behavior is
  unclear, stop and ask rather than inventing an endpoint, schema, or library
  API that "should" exist.
- **Minimize scope.** Ship the smallest change that solves the stated
  problem. Don't bundle a dependency/toolchain upgrade, a refactor, or an
  architecture change into a task that didn't ask for one — each of those is
  its own reviewable unit, and bundling them is exactly how a narrow bug fix
  becomes a broken build (see Incidents).
- **Preserve existing functionality.** Read the whole file you're editing
  before changing it. Understand why the current code does what it does —
  this codebase has a lot of hard-won, non-obvious workarounds (MV3 service
  worker restrictions, WASM loading per platform, CORS routing) that look
  removable but aren't.
- **Verify claims before acting on them, especially dependency versions.**
  If you add or bump a dependency, confirm the exact version you're pinning
  actually exists and actually resolves cleanly in this build (`npm install`
  / a real Gradle sync) before considering the change done. A version number
  that looks plausible is not the same as one that was checked.
- **Validate before declaring anything finished**: `npm run typecheck`,
  `npm test`, and — for anything touching `android/` — an actual Gradle
  build (`cd android && ./gradlew assembleDebug`), not just a web bundle
  build. A change that compiles TypeScript but has never actually run
  through Gradle is not verified.
- **Security-critical surfaces need extra caution, not extra speed.** Vault
  encryption (`crypto-vault.ts`, PBKDF2-600k/AES-GCM), transaction signing
  per chain, the release signing keystore, and anything in the approval/UI
  gating path (`wallet-handlers.ts`) are the parts of this app where a bug
  costs someone their funds. If you're not certain a change in these areas
  is correct, say so explicitly rather than presenting it as done.

## Architecture in one paragraph

Four targets share one `src/main/*` chain-core bundle via **vite alias
seams**, not forks: `chrome-store`/`secure-store` pivots to per-target storage
(`capacitor-store.ts`, extension's own store), `platform` pivots to per-target
side effects, and the extension's `wallet-handlers.ts` `handle()` router is
called directly in-process by both the extension background script and the
native wallet WebViews. If you're implementing something "for Android" or
"for the extension," check whether it already exists in the shared core
before writing target-specific code — most features should need zero
target-specific logic beyond the seam.

**iOS and Android are one target with two alias sets.** Both build from
`src/capacitor/*`; `src/ios/` holds only an entry point, a stylesheet, and the
two modules iOS must replace (`update-check.ts`, `default-browser.ts`). The
alias table and plugin set live in **`vite.capacitor.shared.ts`**, consumed by
both `vite.capacitor.config.ts` and `vite.ios.config.ts` — add a new seam
there, not in one config, or the targets drift. Do **not** fork
`src/capacitor/CapApp.tsx` or any other shared WebView module for iOS; if a
difference can't be expressed as an alias, gate it in place.

## Toolchain facts that will silently break a build if you don't know them

- **Android requires JDK 24**, not 21. `android/app/build.gradle` overrides
  Capacitor's auto-generated `capacitor.build.gradle` (which pins Java 21)
  to Java 24, because `info.guardianproject:tor-android` ships Java 24
  bytecode. If you touch Java version settings, know that
  **`capacitor.build.gradle` is regenerated by every `npx cap sync`** (part
  of `npm run build:capacitor`) — hand-editing it does not stick; overrides
  belong in `app/build.gradle` *after* the `apply from: 'capacitor.build.gradle'`
  line.
- Both `.github/workflows/release.yml` and `build.yml` must have matching
  `java-version` for the Android job — CI uses a fresh checkout, so a
  toolchain requirement that only exists locally will pass for you and fail
  in CI.
- **Test the real Gradle build, not just `npm run build:capacitor`.** The web
  bundle step can succeed while the native Android compile fails outright —
  that gap is exactly what caused the incident below.
- Windows dev machine: `gradlew` needs its executable bit preserved in git
  (`git update-index --chmod=+x android/gradlew`) or CI fails with
  `Permission denied` (exit 126).
- **iOS cannot be built or run on the Windows dev machine.** Xcode and the iOS
  Simulator are macOS-only and no emulator exists for Windows — there is no
  workaround, so do not claim an iOS change is verified without a green
  `Build (iOS)` job. On Windows, `npm run build:ios` is expected to complete
  the vite + esbuild + plist stages and then fail at `cap sync ios`; that is
  success, not a break. The `Build (iOS)` job in `build.yml` compiles unsigned
  against the simulator SDK, so it needs **no Apple account or certificate**.
- The Capacitor CLI has **no `--config` flag**, so both native targets share
  one `capacitor.config.ts` and differ only by `webDir`, which is read from
  `CAP_WEB_DIR`. Always invoke the CLI for iOS through **`node scripts/cap.js
  <cmd> ios`** — a bare `npx cap sync ios` picks up Android's `dist-capacitor`
  and ships the wrong bundle without erroring.
- `npm run icons:ios` **must run after** the platform is added: `cap add ios`
  refuses a non-empty `ios/`, so generating icons first permanently blocks
  scaffolding. The script hard-fails rather than creating the directory.
- `ios.scheme` is pinned to `https` in `capacitor.config.ts`. iOS defaults to
  `capacitor://localhost`, which would invalidate every CORS-verified entry in
  `src/capacitor/fetch-guard.ts`'s `BROWSER_HOSTS` — and the failure mode is
  silent: hosts fall back to the native bridge, which corrupts the binary
  bodies Monero and Zcash depend on. Don't change it without re-verifying that
  allowlist against the new origin.

## Release pipeline — do not bypass the gating

`.github/workflows/release.yml` creates a single **draft** release
(`prepare-release` job) before any builder runs, every build job uploads
into that draft, and a final `publish-release` job verifies all 11 expected
asset patterns exist before flipping the release to published. This exists
because electron-builder silently skips uploads into an already-published
non-draft release — a partial release with green CI is worse than a failed
one. **Never revert to a flow where any single job creates/publishes the
release before all builders have finished.**

Version bumps go through `node scripts/release.js [patch|minor|major|beta]`
— it keeps `package.json`, the extension manifest, and
`android/app/build.gradle`'s versionCode/versionName in sync. Don't bump
these by hand in only one place.

## Real-funds QA gate

`docs/RELEASE-QA.md` is the checklist that must be fully signed off before
any `v1.0.0` tag — every chain's send path needs at least one real (not
testnet) transaction on record. If you implement or change a send path for
any chain, that row needs to be re-tested before shipping, not assumed still
valid.

## Incidents (why some of the above rules exist)

- **2026-07-20**: a fix for Android Tor onion-service connectivity correctly
  swapped `arti-mobile` for `info.guardianproject:tor-android:0.4.9.11`, but
  the change was never run through an actual Gradle build. The new
  dependency's Java 24 bytecode was incompatible with the project's Java 21
  compile target, breaking `assembleDebug`/`assembleRelease`/`bundleRelease`
  outright. The web-bundle step (`npm run build:capacitor`) had passed, which
  is not the same thing as a working Android build — that gap is why "test
  the real Gradle build" above is called out explicitly.
